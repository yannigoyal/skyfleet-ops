## mock-dispatches-wrong-drone — LLM_MOCK chat dispatched a positionally-chosen drone instead of the one the operator named

- **Date:** 2026-08-14
- **Error patterns:** wrong drone dispatched, dispatched drone does not match requested, LLM_MOCK=true, mock_reply, chat auto-execution, silent wrong-entity selection, no exception raised, request succeeds with wrong target, positional default, idle[0], active[0], first idle drone, first active mission, drone_id ignored in user message, keyword-only substring match, FALCON-03 requested FALCON-02 dispatched
- **Root cause(s):** CODE — `mock_reply()` in `backend/app/chat/llm.py` selected the dispatch target positionally (`idle[0]` for launch, `active[0]["drone_id"]` for recall) and never read a drone id out of `user_message`, which it consumed only as a lowercased haystack for the substring tests `"launch" in text` / `"recall" in text`; under `LLM_MOCK=true` this function is the entire decision path (`llm.py:213-214`) and `chat/router.py:146-151` executes its output verbatim, so the wrong drone launched with no error; **AND** TEST-GAP — nothing pinned that selection to the named drone, so the defect survived to UAT. Both conditions were required for the operator to see it: with `LLM_MOCK` unset the real model reads the drone id from the message via the structured-output schema and the positional code is unreachable.
- **Fix:** Added `_named_drone_id(fleet_context, text)` to `backend/app/chat/llm.py` — matches the message against the ids the fleet already knows (roster + active_missions), case-insensitively, longest id first so `FALCON-10` is never read as the `FALCON-1` that prefixes it. `mock_reply` now dispatches that named drone for both launch and recall, demoting the positional selection to a fallback used only when the message names no known drone (preserving the keyword-only prompts `tests/specs/chat.spec.ts` depends on). A named-but-ineligible drone is passed through deliberately so the service layer returns a readable error rather than silently substituting a different drone — the same failure class.
- **Files changed:** backend/app/chat/llm.py, backend/tests/chat/test_llm.py, backend/tests/chat/test_router.py
- **Why not caught:** The **unit test suite** was the gate, and it had a hole exactly the shape of this bug — `mock_reply`'s own drone-selection logic was never exercised by anything. Three separate tests each looked like coverage and provided none: `test_llm.py::TestMockMode` called `mock_reply` but asserted only `isinstance(reply, FlightDirectorReply)` plus that `acompletion` went untouched (it verified the mock was *used*, never *what it chose*); `test_router.py:98` monkeypatched `mock_reply` away entirely, so the API-level chat tests exercised the router against a stub, not the real function; and the eval fixtures in `tests/chat/test_evals.py` force `mock_mode_enabled` to `False`, routing around it. Type checking, lint, and review could not have caught this — the wrong value is a well-typed `str` that is a genuine roster drone id, so the bug is invisible to every gate except a behavioral assertion binding output to input. Generalizable lesson: an `isinstance`-only assertion on a selector function is a coverage mirage — it pins the return *type* while leaving the entire selection *decision* free, and coverage tooling reports the line as covered.
- **Recurrence guard:** Regression tests, verified green at archive time (36 passed). `backend/tests/chat/test_llm.py::TestMockReplyDroneSelection` (12 tests) asserts equality between the drone named in the message and the drone in `reply.missions[0].drone_id` across launch, recall, case-insensitive input, `FALCON-1`/`FALCON-10` prefix ambiguity, named-but-ineligible drones, empty roster, and both no-drone-named fallbacks. `backend/tests/chat/test_router.py::test_mock_launch_dispatches_the_drone_the_operator_named` and `::test_mock_recall_targets_the_drone_the_operator_named` reproduce the reported UAT flow end to end through `POST /api/chat` **without** monkeypatching `mock_reply`, closing the specific hole that let this through. Mutation-tested at the fix site: 4/4 mutants killed (drop longest-first ordering, drop case-insensitivity, ignore named drone on launch, ignore named drone on recall), so the assertions genuinely constrain the logic rather than passing vacuously. Known residual limit, deliberate and documented in the `_named_drone_id` docstring: ids the fleet has never heard of (e.g. `FALCON-99`) still fall back to the positional default, since matching bare hyphen-digit tokens would misfire on zone names like `Riverside-5`.
