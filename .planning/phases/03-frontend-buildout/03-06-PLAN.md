<objective>
Replace the static "not yet implemented" placeholder sidebar with the working AI flight
director: the operator can hold a conversation with the copilot, and every mission or roster
action it takes on their behalf appears inline as a structured confirmation card rather than
buried in prose.

Purpose: this is the phase's headline capability and the last slice of the console. The
backend half has been complete and verified since Phase 2 — `POST /api/chat` executes AI
actions through the identical `missions.service` and `roster.service` functions the dispatch
bar uses. What is missing is the surface that lets the operator see what the copilot
actually did, which is exactly what FE-09's confirmation cards exist to provide in place of
the deliberately-omitted confirmation dialog.
Output: a docked, collapsible chat sidebar wired to the shared fleet refetch, with inline
action confirmations.
</objective>

<planner_assumptions>
**Flagged assumption — FE-09 edge coverage is unresolved.** The deterministic edge-probe
classified FE-09 (inline confirmation cards) as `unclassified` — no shape cue in the
requirement text matched an applicable category, so nothing was auto-derived or
auto-resolved. Surfaced rather than dropped. The planner's working assumption is that
FE-09's real edge is **not a data shape but a response-contract gap**: research verified
that `POST /api/chat` returns `errors` as a flat array of human-readable strings with no
association back to a specific action, so a failed action cannot be paired with the action
that failed. This plan handles that by treating every entry in `missions`/`roster_changes`
as a success card and every `errors` string as an independent failure card — the only
correct reading of the response shape — and records the risk of getting this wrong as this
plan's prohibition. A per-action error association would require a backend response-shape
change, which is out of this frontend-only phase's boundary. If a reviewer identifies a
further FE-09 edge, it belongs in gap closure.

**Canon-referral breadcrumb (not minted as a project prohibition).** Reflected XSS via
rendering LLM- or operator-authored text as raw HTML is canon, already documented in
`03-RESEARCH.md` § Security Domain and carried in this plan's `<threat_model>` as T-03-23;
it is covered by `/gsd-secure-phase` and standard lint rules, so per the prohibition-probe
canon-referral rule it is not re-minted as a bespoke project prohibition here.
</planner_assumptions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM-generated text → browser DOM | Model output is the least-trusted string in the system and is rendered directly in the transcript |
| Operator chat input → backend prompt → DOM | Operator text is echoed into the transcript and reaches the model as prompt content |
| AI-proposed action outcomes → operator's belief about fleet state | Confirmation cards are the only signal that an AI action did or did not execute |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-23 | Tampering | LLM `message` text and operator input rendered in `ChatMessage` | high | mitigate | Render every message string as a plain JSX text child, which React escapes by default. No component under `src/components/chat/` uses a raw-HTML rendering prop, asserted by a negative gate in Task 2's acceptance criteria, and behavior test 6 proves an HTML-looking substring renders as visible text with no element created. |
| T-03-24 | Tampering | Multi-byte text truncation in the transcript | medium | mitigate | Assistant content is never truncated (it is the primary content; the bubble wraps at ~85% width instead). Where truncation is used at all — the zone field in a confirmation card — it is CSS ellipsis on a max-width, never index or byte arithmetic that could split a surrogate pair or grapheme cluster. |
| T-03-25 | Repudiation | A failed AI action presented as executed | high | mitigate | Only entries the backend actually returned in `missions`/`roster_changes` may carry a success badge; every string in the flat `errors` array renders as its own equally-weighted failure card. Recorded as this plan's judgment-tier prohibition, and pinned by behavior test 5 (one execution plus one error renders exactly two cards, neither omitted). |
| T-03-26 | Elevation of Privilege | AI-issued actions bypassing dispatch validation | high | mitigate | No mitigation is needed in this plan's code, and none is added: `POST /api/chat` executes every AI-proposed action through the identical `missions.service` / `roster.service` functions manual dispatch uses, enforced server-side by Phase 2's AST import-boundary test and two-database differential test. The frontend only renders the returned arrays — it must never construct a dispatch of its own from an AI-proposed action. |
| T-03-27 | Information Disclosure | Chat transport error surfaced to the operator | low | mitigate | The transport-failure path renders a fixed UI-SPEC copy string, never the raw exception, response body, or request URL, so no internal detail or credential material can reach the transcript. |
| T-03-28 | Denial of Service | Rapid repeated chat sends | low | mitigate | D-08's in-flight lock makes a second send a no-op while a request is outstanding, so a held Enter key cannot fan out concurrent LLM calls. The backend additionally caps `message` at 4000 characters. |
