<objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator free-text `zone` → missions table DOM | An unbounded operator-authored string is rendered in a table cell |
| Backend mission payload → DOM | `distance_km`, `energy_cost_kwh`, and `eta_minutes` are rendered as numerals |
| Client-inferred mission status → operator's mental model | The `delivered` status is derived from a polling delta, not asserted by the server |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-09 | Tampering | Zone free-text cell in `MissionsTable` | medium | mitigate | Render the zone as a plain JSX text child (React escapes text nodes), constrain it with `truncate max-w-[12rem]`, and expose the full value only through a `title` attribute. A negative gate in the acceptance criteria asserts no raw-HTML injection prop appears in the file. |
| T-03-10 | Tampering | Numeric mission fields rendered into table cells | low | mitigate | Format every numeric through `.toFixed(n)` before rendering, matching the `FleetRosterPanel` precedent, so a non-finite value arriving from a future compromised or buggy path cannot render as raw `NaN`/`Infinity`. The backend already guards this at the Pydantic and `isfinite` layers (Phase 2 code review). |
| T-03-11 | Repudiation | Client-inferred `delivered` status | medium | mitigate | The inference is unavoidable this phase (no backend all-statuses endpoint exists and backend changes are out of scope), so it is recorded as an explicit judgment-tier prohibition rather than silently accepted, and the long-term fix — a `GET /api/fleet/missions` returning all statuses — is documented in `03-RESEARCH.md`'s Architectural Responsibility Map for a later phase. |
| T-03-12 | Elevation of Privilege | Recall path bypassing validation | high | mitigate | Recall issues a plain `DELETE` to the existing router and surfaces whatever it returns; `missions/service.recall_mission` remains the sole authority. No client-side "is this drone recallable" check exists, per D-14, so the client cannot grant itself a recall the server would refuse. |
| T-03-13 | Denial of Service | Unbounded mission accumulation over a long session | low | accept | The accumulated map grows only with real dispatch actions in a single-operator demo session and is cleared on reload; the table's internal scroll container bounds the rendered DOM regardless of map size. |
</threat_model>
