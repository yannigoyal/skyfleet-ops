<objective>
Wire the real LiteLLM to OpenRouter to Cerebras call behind the `generate_reply` seam, with the
structured-output schema and provider routing forced through `extra_body`, and lock that shape in
with a unit-level regression gate plus one executed live smoke run.

Purpose: CHAT-08 is the load-bearing risk of this phase and the blocker `STATE.md` has carried since
roadmap creation. LiteLLM's OpenRouter adapter gates `response_format` on an internal provider
allowlist that does not include OpenRouter, so a top-level `response_format` keyword argument is
silently dropped and the model reverts to prompt-only JSON compliance — which looks fine in casual
testing and breaks on exactly the edge-case phrasing where hallucinated actions are most likely. This
plan makes the correct nesting the only shape the code can take, and proves it against the real
endpoint rather than against documentation.

Output: the real branch of `generate_reply`, `test_llm.py` asserting on the recorded call kwargs, the
`live` pytest marker with default deselection, and a gated `test_live_smoke.py` executed once with a
real key and its raw JSON output captured as verification evidence.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Backend → OpenRouter/Cerebras HTTPS endpoint | Operator chat text and fleet state leave the machine; a bearer credential is attached |
| `OPENROUTER_API_KEY` in `.env` → process environment → request headers | A secret crosses from disk into an outbound request |
| Provider response → `parse_reply` | Untrusted remote content enters the application and becomes proposed actions |

Out of scope project-wide: ASVS V2 Authentication, V3 Session Management, V4 Access Control, V6
Cryptography (single-operator demo, no auth boundary).

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Information Disclosure | `OPENROUTER_API_KEY` reaching logs or a response body | high | mitigate | The key is read from the environment per call into a local variable and passed only as the `api_key` argument. No logging statement in `llm.py` includes the key, the request headers, or the full call kwargs; the live smoke prints only the reply body and elapsed time. Plan 04 adds an assertion that the key value is absent from `caplog.text` and every response body across the whole chat suite |
| T-02-08 | Tampering | Provider response content driving proposed actions | high | mitigate | `parse_reply` validates into typed Pydantic models before any field is read, and raises `LLMError` on any structural failure so zero actions execute from a partially-valid reply. Schema-valid but semantically false values are still rejected downstream by `missions.service` / `roster.service` — shape validation is never treated as sufficient |
| T-02-09 | Denial of Service | Degenerate completion running toward the context ceiling | medium | mitigate | `max_tokens=800` and `temperature=0.2` are fixed on every call and asserted in the kwarg-shape gate, bounding a repetitive generation that could otherwise cost roughly 160 times a normal turn and stall the operator's chat |
| T-02-10 | Spoofing | OpenRouter routing the request to an unintended inference provider | medium | mitigate | `provider: {"only": ["Cerebras"]}` pins the upstream provider explicitly rather than relying on auto-selection, and the live smoke's latency reading is the observable check that the pin landed |
| T-02-11 | Information Disclosure | Operator conversation text transmitted to a third party | low | accept | Sending the turn to OpenRouter is the feature; no other egress exists. Recorded as an accepted, disclosed data flow — the prohibition in this plan's must_haves forbids adding any further sink |
| T-02-SC | Tampering | npm/pip/cargo installs | n/a | accept | This plan installs no new package — `litellm` was added under plan 01's blocking legitimacy checkpoint, and the optional Arize Phoenix tooling in AI-SPEC §5 is deliberately not adopted |
</threat_model>
