<objective>
Extend the proven chat turn from launch-only to the full action surface: the flight director can
recall a mission and add or remove a roster drone, and every one of those mutations travels the exact
service-layer function the manual REST endpoints call.

Purpose: this is the phase's highest-risk regression. The sibling-branch reference implementation
calls the roster persistence layer directly from the chat router, which skips the auto-recall-before-
remove guard Phase 1 built — so removing a drone with an active mission through chat would orphan an
`en_route` mission while the same removal through `DELETE /api/roster/{drone_id}` cleans up correctly.
Because both call shapes are valid, importable, and near-identically named, this is an easy mistake to
reproduce while reusing working reference code. This plan makes the correct boundary the only one the
file can express, and proves parity with a differential test rather than an assertion of intent.

Output: the recall branch and the roster-change helper in `chat/router.py`, plus the test class that
runs the same roster removal through both entry points and asserts identical final database state.
</objective>
