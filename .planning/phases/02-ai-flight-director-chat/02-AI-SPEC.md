## 1. System Classification

**System Type:** Hybrid (Conversational assistant + Structured extraction) — a single-turn LLM call per chat message that returns one structured JSON reply combining a conversational message with proposed mission/roster actions. NOT an Autonomous Agent: there is no multi-step planning loop, no agent-initiated tool-calling round-trip, and no persistent agent state — the backend parses the structured reply once and executes proposed actions directly.

**Description:**
The AI flight director is a chat copilot for a single dispatcher operating a simulated 10-drone delivery fleet. Each operator message triggers one LLM call carrying a fresh fleet-state snapshot (budget, roster, live telemetry) plus the last 20 conversation turns; the model returns one structured JSON object containing a conversational `message` plus optional `missions` and `roster_changes` arrays. The backend — not the model — executes those proposals, routing every one through the identical `missions.service` / `roster.service` functions the manual dispatch bar calls, and returns the narrated result plus any per-action errors. "Good" is: the operator says "launch FALCON-03 to Riverside, 4.2 km" (or "which drone should take the next run?") and gets a reply that (a) proposes only actions grounded in real fleet state, (b) executes them under exactly the same validation a human click would face, and (c) names in plain language what actually happened — including what was refused and why.

**Critical Failure Modes:**
<!-- Confirmed by `gsd-eval-planner` from the Section 1b domain evidence; each maps to a Section 5 eval dimension and a Section 6 guardrail. -->
1. **Ungrounded action executed** — a schema-valid but semantically false action (nonexistent `drone_id`, fabricated zone, negative/absurd `distance_km`) reaches a database write because "it matched the schema" was treated as sufficient validation. (Section 1b failure mode 1; eval dimension D1.)
2. **Validation bypass / constraint drift** — a chat-issued action takes a looser write path than the manual REST equivalent (the concrete instance: calling `roster.repository` instead of `roster.service`, skipping the Phase-1 auto-recall-before-remove guard), so AI and human dispatch produce different outcomes for the same request. (Section 1b failure mode 3 + `02-RESEARCH.md` Pitfall 1; eval dimension D2.)
3. **Silent or opaque failure** — a rejected action is dropped from the reply with no mention, or a malformed completion 500s the endpoint, leaving the operator with no idea what did or did not execute. (CHAT-07; eval dimensions D4, D5.)
4. **Structured-output enforcement silently regressing to prompt-only compliance** — `response_format` stops reaching OpenRouter (top-level instead of nested in `extra_body`, or a LiteLLM upgrade changing the passthrough), so replies are "usually JSON because the prompt asked" rather than schema-constrained — intermittently malformed exactly on the edge-case phrasing where failure modes 1-3 are most likely. (Section 1b failure mode 4 + `02-RESEARCH.md` Pitfall 5 / CHAT-08; eval dimension D3.)
5. **Incoherent multi-action turn** — several actions in one reply execute without regard to order or each other's side effects, leaving fleet/budget state inconsistent with what the `message` claims happened. (Section 1b failure mode 2; eval dimension D6.)

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Fleet-operations dispatch / agentic developer tooling. SkyFleet Ops is an explicitly simulated, single-operator drone-delivery demo capstone for an agentic-AI coding course — not an operational aviation or logistics deployment. There are no real drones, no real deliveries, a virtual 500 kWh energy budget, and no auth/multi-tenant boundary. The relevant practitioner lens is therefore not "drone-delivery compliance" but "what a dispatch-operations copilot must get right architecturally" — the same validated-action-execution pattern that would carry real stakes in an actual fleet-ops, logistics-dispatch, or IT-ops copilot, demonstrated here in a zero-stakes sandbox for pedagogical purposes (per `REQUIREMENTS.md` Out of Scope: "stakes are zero (simulated fleet/budget)").

**User Population:** A single dispatcher/operator (the course learner, in practice) interacting with the AI flight director through natural-language chat, delegating the same mission-launch/recall and roster add/remove actions available through the manual dispatch bar (`FE-06`). No other users, no role separation, no concurrent multi-operator contention — `operator_id="default"` throughout.

**Stakes Level:** Low (operational/business impact — simulated fleet, virtual budget, single-session demo, explicitly zero real-world consequence per `PLAN.md` §9 and `REQUIREMENTS.md`). **Architectural stakes are treated as High for evaluation-design purposes** — the auto-execute-with-no-confirmation-dialog design (`FE-06`, `REQUIREMENTS.md` Out of Scope) means every AI-proposed action reaches the database with no human checkpoint, so the system must demonstrate the same validated-boundary rigor a real high-stakes agentic system would need, even though a mistake here costs nothing but a wrong number on a demo screen.

**Output Consequence:** An AI-proposed action (`missions` or `roster_changes` array entry in the structured JSON reply) is auto-executed immediately by the backend through `missions.service`/`roster.service` — the identical functions the manual REST endpoints call (CHAT-02–CHAT-04) — with no confirmation dialog. Downstream effects are: a mission row created/updated, the virtual energy budget debited, a roster drone added/removed (with auto-recall of its active mission first, per the Phase-1 D-03 guard), and an inline confirmation card rendered in the chat transcript (`FE-09`, built in Phase 3) summarizing what executed. A failed/invalid proposal must surface as a readable chat-visible error (CHAT-07), never a silent drop or an unhandled crash.

### What Domain Experts Evaluate Against

```
Dimension: Action grounding fidelity (no hallucinated drone/zone/argument)
Good: Every proposed drone_id exists on the current roster, every zone/distance is plausible for the fleet context the model was given, and the action type (launch/recall/add/remove) matches what the operator actually asked for or the fleet state actually supports (e.g., "recall" only proposed for a drone that is genuinely en_route)
Bad: A syntactically valid but non-existent drone_id, a fabricated zone name, a negative/absurd distance_km, or an action type that doesn't match fleet reality (e.g., proposing to recall a drone that was never launched)
Stakes: Critical
Source: Industry agent-evaluation research — "right tool, wrong arguments" is documented as the most common production agentic-system bug (argument/entity hallucination that passes schema validation but fails semantic grounding); this system's structured-output schema (CHAT-08) constrains shape only, not truthfulness

Dimension: Execution transparency (does the reply narrate what actually happened)
Good: The `message` field names the specific drone(s), action(s), and outcome in plain language clearly enough that a dispatcher reading only the chat transcript — not the raw JSON or the missions table — knows exactly what executed and why (this is what FE-09's inline confirmation cards render from)
Bad: A vague acknowledgement ("Done!" or "I've made some changes") that doesn't name which drone/zone/action executed, forcing the operator to cross-reference the missions table to reconstruct what the AI actually did
Stakes: High
Source: Dispatcher/copilot trust research — audit-trail-style reasoning transparency is the documented substitute for a confirmation gate in agentic copilots that auto-execute; this project deliberately chose "rich inline confirmation cards" over a blocking dialog (`REQUIREMENTS.md` Out of Scope), which only works if `message` actually carries that narrative detail

Dimension: Constraint parity with manual dispatch (identical validation, no shortcut path)
Good: An AI-proposed action that would fail manual validation (insufficient budget, drone already en_route, unknown drone, drone not currently in flight for a recall) fails identically when proposed by the AI, via the same `missions.service`/`roster.service` functions — never a second, looser "trusted because the AI reasoned about it" write path
Bad: An AI-proposed action succeeds or fails differently than the equivalent manual action would (e.g., chat-issued roster removal skips the auto-recall-before-remove guard that manual `DELETE /api/roster/{drone_id}` enforces)
Stakes: Critical
Source: Structural-guardrail research — "policy enforcement out of the prompt window and into deterministic runtime execution gateways" is the documented best practice for agentic action systems; directly matches this phase's own validated-boundary pattern (CHAT-02–CHAT-04, `02-RESEARCH.md` Pattern 1) and its own flagged regression risk (Pitfall 1: chat bypassing `roster.service` for `roster.repository`)

Dimension: Failure legibility (rejected actions are understandable, not silent or opaque)
Good: When a proposed action fails validation, the chat response names the drone and the specific reason in operator-readable language (e.g., "Could not launch FALCON-03 to Riverside: insufficient energy budget") rather than a raw exception string or a generic failure
Bad: A failed action is silently dropped from the reply with no mention, or surfaces only as a generic "something went wrong" with no drone/action/reason named
Stakes: High
Source: CHAT-07 requirement ("the error is included in the chat response so the LLM can inform the operator"); matches the industry "error recovery" dimension in agent-trajectory evaluation frameworks

Dimension: Non-contradictory batch execution (multi-action replies behave consistently)
Good: When one reply proposes multiple actions, each executes sequentially against live state, so a later action in the same reply can correctly fail if an earlier one already consumed the budget or changed drone eligibility — not treated as a pre-validated all-or-nothing batch
Bad: Contradictory actions proposed in the same turn (e.g., launch and recall for the same drone) execute without regard to order or side effects, leaving an inconsistent fleet/budget state
Stakes: Medium
Source: `02-RESEARCH.md` Pitfall 3 — explicit guidance that multi-action replies must execute one action at a time through the shared budget-checking path, not as a batch
```

### Known Failure Modes in This Domain

1. **Hallucinated but schema-valid arguments** — the model emits a `drone_id`, `zone`, or `distance_km` that satisfies the JSON schema's type/enum constraints but does not correspond to real fleet state (nonexistent drone, fabricated zone, implausible distance). This is the dominant documented failure mode for tool-calling/structured-extraction agents generally, not specific to drones — the risk here is structural (schema compliance ≠ semantic truth), and the only mitigation is the service-layer re-validation this phase already requires (Pattern 1).
2. **Contradictory or nonsensical multi-action replies** — a single structured reply proposes internally inconsistent actions (e.g., recall and launch the same drone in one turn, or add and immediately remove the same roster entry), which schema validation cannot catch because each individual action is independently well-formed.
3. **Auto-execution removing the human check that would normally catch mistakes** — because there is no confirmation dialog (a deliberate project decision), any gap in service-layer validation becomes an immediately-executed state change rather than a caught error before it happens. This raises the bar on the validated-boundary pattern's completeness even though the simulated consequences are low-stakes — the pattern itself is what a real deployment would depend on.
4. **Provider-side structured-output enforcement silently degrading to prompt-only compliance** — the project's own research (CHAT-08, `02-RESEARCH.md` Pitfall 5) found that LiteLLM's OpenRouter adapter can silently drop the `response_format` constraint unless nested in `extra_body`; if that regresses, the model's replies become "usually JSON because the system prompt asked for it" rather than schema-enforced, which produces intermittent malformed completions specifically on edge-case phrasing — exactly the condition under which hallucinated/contradictory actions (failure modes 1–2) become more likely, not less.

### Regulatory / Compliance Context

None identified — and none should be imported. This is an explicitly simulated, single-operator, no-auth course capstone with a virtual energy budget and no real drones or deliveries; `PLAN.md` §9 and `REQUIREMENTS.md`'s Out of Scope table state the zero-confirmation auto-execution design is deliberate specifically *because* "stakes are zero (simulated fleet/budget)." Real-world drone-delivery/aviation regulation (e.g., FAA Part 107) does not apply to this system and is deliberately excluded from this evaluation's scope — treating it as a literal compliance constraint would misrepresent what this system is. What this domain research instead grounds is the architectural pattern a real regulated fleet-ops or logistics-dispatch copilot would need (validated-boundary execution, auditable reasoning, service-layer parity) — the course's pedagogical point is demonstrating that pattern correctly even where the real-world consequence is nil.

## 2. Framework Decision

**Selected Framework:** LiteLLM (direct `litellm.acompletion()` call, no orchestration framework) + Pydantic for structured-output validation

**Version:** `litellm>=1.96.0`, `pydantic==2.13.4` (already installed transitively via FastAPI)

**Rationale:**
This is one LLM call per chat turn returning one structured JSON object — there is no agent loop, no retrieval, no multi-agent handoff, and no state graph for an orchestration framework to manage. Every orchestration framework would also have to displace LiteLLM, which `planning/PLAN.md` §9 and `.claude/CLAUDE.md` fix as the mandated client (not an open decision for this phase), and would want to own the tool-execution path that CHAT-02..04 explicitly require to route through the existing `missions.service`/`roster.service` — an orchestration framework's own tool-calling loop would compete with that requirement rather than serve it. Choosing "no framework" makes `chat/llm.py` the single provider seam, which is what makes both the `LLM_MOCK` early-return and a future provider swap cheap.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain | Displaces the mandated LiteLLM client; simple single-call chatbot gets zero benefit from the abstraction overhead |
| LangGraph | Displaces LiteLLM; its checkpointer wants Postgres/Redis vs. this project's SQLite-only constraint; no branching graph exists — one linear call |
| CrewAI | Displaces LiteLLM; no multi-agent roles exist in this phase — one director, one call |
| LlamaIndex | No RAG, no documents, no vector store — fleet context is a live struct read from `TelemetryCache` + SQLite, not retrieved |
| OpenAI Agents SDK / Claude Agent SDK / Google ADK | Displaces LiteLLM; each is provider-pinned (OpenAI/Anthropic/Gemini) while the model is fixed to `gpt-oss-120b` via OpenRouter/Cerebras; their tool-execution loops would own the write path, conflicting with CHAT-02..04's service-layer delegation requirement |
| AutoGen / AG2, Haystack | Displaces LiteLLM; no fit for a single-call structured-extraction shape (no multi-agent conversation loop, no NLP pipeline need) |
| raw `httpx` POST to OpenRouter REST | Viable but strictly more code than LiteLLM for the same benefit, and LiteLLM is already the fixed project choice |
| `openai` SDK 2.54.0 pointed at OpenRouter's `base_url` (escape hatch, not primary) | Not ruled out — held as the documented fallback if the CHAT-08 live smoke test shows LiteLLM's OpenRouter adapter still strips `response_format` even nested in `extra_body`. The `openai` SDK honors `response_format` natively (already installed as a LiteLLM transitive dependency) but adopting it requires lifting the PLAN.md §9 LiteLLM constraint, so it is not adopted unless the primary pick is empirically proven to fail. |

**Vendor Lock-In Accepted:** Partial — locked to LiteLLM's request/response shape and to OpenRouter as the routing layer (both already fixed by project-level constraints predating this phase, not introduced by this decision). Not locked to any single underlying model provider: LiteLLM's `model=` string and OpenRouter's `provider` routing make swapping the underlying inference provider (away from Cerebras) or the model itself a config change, not a rewrite.

### Core Imports

```python
import json
import os

import litellm
from pydantic import BaseModel, Field, ValidationError
```

### Entry Point Pattern
```python
# backend/app/chat/llm.py — minimal working example for this system type
# (Hybrid: single-turn conversational reply + structured mission/roster extraction)

SYSTEM_PROMPT = (
    "You are SkyFleet flight director, an AI fleet operations assistant. "
    "Analyze fleet battery health, mission load, and remaining energy budget. "
    "Suggest mission launches/recalls with reasoning. Execute missions when the "
    "operator asks or agrees. Be concise and data-driven. Always respond with "
    "valid structured JSON matching the provided schema."
)

class MissionAction(BaseModel):
    drone_id: str
    action: str            # "launch" | "recall"
    zone: str | None = None
    distance_km: float | None = None

class RosterChange(BaseModel):
    drone_id: str
    action: str             # "add" | "remove"

class FlightDirectorReply(BaseModel):
    message: str
    missions: list[MissionAction] = Field(default_factory=list)
    roster_changes: list[RosterChange] = Field(default_factory=list)

class LLMError(Exception):
    """Raised when the LLM's completion fails schema validation."""


def mock_mode_enabled() -> bool:
    return os.environ.get("LLM_MOCK", "").strip().lower() == "true"


def parse_reply(raw_content: str) -> FlightDirectorReply:
    try:
        payload = json.loads(raw_content)
    except (json.JSONDecodeError, TypeError) as exc:
        raise LLMError(f"non-JSON completion: {exc}") from exc
    payload.setdefault("missions", [])
    payload.setdefault("roster_changes", [])
    try:
        return FlightDirectorReply.model_validate(payload)
    except ValidationError as exc:
        raise LLMError(f"schema validation failed: {exc}") from exc


async def generate_reply(
    fleet_context: str, history: list[dict], user_message: str
) -> FlightDirectorReply:
    if mock_mode_enabled():
        return FlightDirectorReply(message="Mock flight director reply.")

    response = await litellm.acompletion(
        model="openrouter/openai/gpt-oss-120b",
        api_key=os.environ["OPENROUTER_API_KEY"],
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "system", "content": fleet_context},
            *history,
            {"role": "user", "content": user_message},
        ],
        temperature=0.2,
        max_tokens=800,
        # response_format MUST be nested in extra_body for openrouter/* models —
        # see Common Pitfalls #1. provider.only forces Cerebras inference, no auto-detection.
        extra_body={
            "response_format": {"type": "json_schema", "json_schema": RESPONSE_SCHEMA},
            "provider": {"only": ["Cerebras"]},
        },
    )
    raw_content = response.choices[0].message.content
    return parse_reply(raw_content)
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `litellm.acompletion()` | Async, provider-agnostic chat-completion call; returns an OpenAI-shaped `ModelResponse` regardless of underlying provider | The single LLM call site, once per chat turn, in `chat/llm.py::generate_reply()` |
| `extra_body` | Passthrough dict LiteLLM merges directly into the raw HTTP request body, bypassing its internal per-provider parameter allowlist | Required here because a top-level `response_format` kwarg is silently dropped for `openrouter/*` models — nesting it in `extra_body` forces it through regardless of LiteLLM's provider support matrix |
| `model="openrouter/<vendor>/<model>"` string routing | LiteLLM's `<provider>/<model>` prefix selects the OpenRouter adapter; everything after `openrouter/` is passed through verbatim as OpenRouter's own model id | Selecting `openai/gpt-oss-120b` via OpenRouter rather than a direct provider SDK |
| `extra_body["provider"]` (OpenRouter provider routing) | OpenRouter-native routing hint (`{"only": [...]}`) that pins which upstream inference provider serves the request | Forcing Cerebras inference specifically, instead of OpenRouter's default provider auto-selection (CHAT-08) |
| Pydantic `model_validate()` | Parses and validates a `dict` against a typed schema, raising `ValidationError` on shape mismatch | Immediately after every `acompletion()` call, before any proposed action is executed — the second, independent validation layer beyond the provider's own `strict:true` schema enforcement |

### Common Pitfalls
1. **Passing `response_format` as a top-level kwarg to `acompletion()` for `openrouter/*` models — silently stripped.** LiteLLM gates whether it forwards `response_format` on an internal `supports_response_schema()` provider allowlist that does not include OpenRouter (confirmed live via `docs.litellm.ai/docs/completion/json_mode` this session — OpenRouter is absent from the listed supported-provider set: OpenAI, Azure, xAI, Google AI Studio, Vertex AI, Bedrock, Anthropic API, Groq, Ollama, Databricks). The model still receives instructions to emit JSON via the system prompt and may "usually" comply — masking the bug until an edge-case prompt breaks it. **Fix:** nest `response_format` inside `extra_body` (see Entry Point Pattern).
2. **Case-sensitivity of OpenRouter provider-routing names.** Cerebras's own integration docs use capitalized `"Cerebras"` in `provider: {"only": [...]}`; whether OpenRouter's matcher is case-insensitive is undocumented. Match the authoritative capitalization exactly rather than relying on unverified case tolerance, and confirm with a live (non-mocked) smoke-test call before trusting it in CI.
3. **Treating "the JSON parsed" as full validation.** `strict:true` JSON-schema mode constrains *shape* (field names, types, enum values), not *truthfulness* — a syntactically valid `drone_id` can still be one that was never on the roster, or `distance_km` can be a schema-valid negative number. Never execute a parsed action without also passing it through the real domain service (`missions.service` / `roster.service`); do not add a second, weaker semantic-validation layer in `chat/llm.py` and treat it as sufficient.
4. **Calling `asyncio.run()` around `generate_reply()` from inside a FastAPI route handler.** FastAPI route handlers already execute inside uvicorn's running event loop; wrapping an async call in `asyncio.run()` there raises `RuntimeError: asyncio.run() cannot be called from a running event loop`. Always `await generate_reply(...)` directly.
5. **Leaving `max_tokens` unset.** `gpt-oss-120b`'s context window is 131,072 tokens end to end — an unbounded call on a degenerate completion (e.g., repetition) can run to that ceiling, multiplying per-call cost and latency by orders of magnitude for a single malformed generation. Always set `max_tokens` explicitly (800 is enough headroom for one `FlightDirectorReply`).

## 4. Implementation Guidance

**Model Configuration:**
- `model="openrouter/openai/gpt-oss-120b"` — fixed by `planning/PLAN.md` §9 and `.claude/CLAUDE.md`; not an open decision for this phase.
- `temperature=0.2` — this is a structured-extraction-plus-dispatch task, not creative writing; a low temperature reduces turn-to-turn variance in which `drone_id`/`action` gets proposed for the same fleet state, which matters because proposals auto-execute with no confirmation gate.
- `max_tokens=800` — a `FlightDirectorReply` is one short message plus at most a handful of mission/roster objects; 800 gives comfortable headroom while keeping the 131,072-token ceiling explicitly bounded (Common Pitfall #5).
- `api_key=os.environ["OPENROUTER_API_KEY"]` — read once per call from the project `.env`; never logged (see Section 4b.5 and the Security Domain analysis in `02-RESEARCH.md`).
- `extra_body={"response_format": {...}, "provider": {"only": ["Cerebras"]}}` — the only place schema enforcement and provider routing are configured; both must stay nested here, not top-level (Common Pitfall #1).
- `stream=False` (the default — not set explicitly) — PLAN.md §9 returns one complete JSON response per turn; a loading indicator substitutes for token-by-token streaming.

**Core Pattern:**
LLM proposes, service layer executes (validated-boundary pattern — see `02-RESEARCH.md` Pattern 1). `chat/router.py` never writes to the database directly and never re-implements budget/eligibility/roster checks:
```python
# backend/app/chat/router.py (sketch)
async def post_chat(db, cache, source, request: ChatRequest) -> dict:
    fleet_context = await build_fleet_context(db, cache)
    history = await repository.get_recent_messages(db, limit=20)
    reply = await llm.generate_reply(fleet_context, history, request.message)

    executed_missions, mission_errors = [], []
    for action in reply.missions:
        result, error = await _execute_mission(db, cache, action)
        (executed_missions if result else mission_errors).append(result or error)

    executed_roster, roster_errors = [], []
    for change in reply.roster_changes:
        result, error = await _execute_roster_change(db, source, change)
        (executed_roster if result else roster_errors).append(result or error)

    await repository.append_message(db, "user", request.message, actions=None)
    await repository.append_message(
        db, "assistant", reply.message,
        actions={"missions": executed_missions, "roster_changes": executed_roster},
    )
    return {
        "message": reply.message,
        "missions": executed_missions,
        "roster_changes": executed_roster,
        "errors": mission_errors + roster_errors,
    }
```
Every action, regardless of source, passes through the exact same `missions.service.launch_mission()` / `recall_mission()` and `roster.service.add_drone()` / `remove_drone()` functions the manual REST routers already call (CHAT-02/03/04) — see `02-RESEARCH.md` Pattern 1 and Pitfall 1 for the roster-service-not-repository requirement.

**Tool Use:**
No native LLM tool-calling / function-calling loop is used. The model is not given tool definitions to invoke; it produces one structured JSON object per turn (`message` + `missions` + `roster_changes`), and the *backend* — not the model — decides what to execute, delegating to `missions.service`/`roster.service`. This is deliberate: PLAN.md's "one call per chat turn" and "auto-execute, no confirmation" requirements are simpler to guarantee correct with a single structured-output round trip than with a model-driven tool-call loop, which would need its own confirmation/error-recovery handling and would risk the tool-execution path competing with the service-layer delegation CHAT-02..04 require. If provider-native tool-calling for `gpt-oss-120b` is ever adopted, it must still route every tool result through the same service layer — never execute directly from a tool-call response.

**State Management:**
`chat_messages` (existing schema — no migration needed) is the durable store; `chat/repository.py`'s `append_message()`/`get_recent_messages()` are the only persistence code this phase adds. There is no in-memory session or server-side conversation/thread object — every turn independently reloads the last 20 messages plus a fresh fleet-state snapshot (`build_fleet_context()` reading `TelemetryCache` + SQLite), so state survives restarts and needs no sticky-session handling. The LLM itself is stateless between calls; the full replayed history is re-sent as `messages` on every turn.

**Context Window Strategy:**
`gpt-oss-120b`'s context window is 131,072 tokens (verified via OpenRouter's model page this session). At this phase's scale — a 10-drone fleet snapshot, a 20-message history cap, one operator message — the full prompt is well under 5-10K tokens; no chunking, reranking, or summarization is required. `get_recent_messages(db, limit=20)` bounds history growth so token cost and latency stay flat regardless of session length. A future phase could add summarization if 20 turns proves insufficient, but nothing in Phase 2's scope requires it.

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

```python
# backend/app/chat/llm.py — output schema for this system type (Hybrid: chat + extraction)
from pydantic import BaseModel, Field

class MissionAction(BaseModel):
    drone_id: str
    action: str                       # "launch" | "recall"
    zone: str | None = None
    distance_km: float | None = None

class RosterChange(BaseModel):
    drone_id: str
    action: str                       # "add" | "remove"

class FlightDirectorReply(BaseModel):
    message: str
    missions: list[MissionAction] = Field(default_factory=list)
    roster_changes: list[RosterChange] = Field(default_factory=list)

# The JSON-schema counterpart sent to the provider (must mirror the Pydantic
# shape field-for-field; strict:true requires every `properties` key to also
# appear in `required`, so optional fields are typed nullable, not omitted).
RESPONSE_SCHEMA = {
    "name": "flight_director_reply",
    "strict": True,
    "schema": {
        "type": "object",
        "properties": {
            "message": {"type": "string"},
            "missions": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "drone_id": {"type": "string"},
                        "action": {"type": "string", "enum": ["launch", "recall"]},
                        "zone": {"type": ["string", "null"]},
                        "distance_km": {"type": ["number", "null"]},
                    },
                    "required": ["drone_id", "action", "zone", "distance_km"],
                    "additionalProperties": False,
                },
            },
            "roster_changes": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "drone_id": {"type": "string"},
                        "action": {"type": "string", "enum": ["add", "remove"]},
                    },
                    "required": ["drone_id", "action"],
                    "additionalProperties": False,
                },
            },
        },
        "required": ["message", "missions", "roster_changes"],
        "additionalProperties": False,
    },
}
```

**How the framework integrates:** No orchestration framework wraps this — there is no `.with_structured_output()` (LangChain) or `PydanticOutputParser` (LlamaIndex) here, and `instructor` is not used either, since LiteLLM's own `extra_body["response_format"]` already asks the provider to constrain generation at the token level. Validation is two independent layers: (1) the provider's own `strict:true` JSON-schema enforcement (best-effort — see Section 3 Common Pitfall #1, since LiteLLM's OpenRouter adapter doesn't natively support this parameter and requires the `extra_body` workaround to even request it), and (2) `FlightDirectorReply.model_validate()` in `chat/llm.py::parse_reply()`, which re-validates the parsed JSON independently and is the layer actually trusted — layer (1) reduces how often layer (2) fails, it does not replace it.

**Retry logic:** Zero automatic retries against the LLM in Phase 2. `parse_reply()` wraps `json.loads()` and `model_validate()` in `try/except`, raising a single `LLMError` on any failure (non-JSON content, missing `message`, invalid `action` enum value, wrong types). The router catches `LLMError` and returns `HTTPException(502, {"reason": "llm_unavailable", ...})` — a clean, chat-visible failure (CHAT-07), never a silent retry or a partial/garbage execution. Log the raw failed `content` string at INFO level for diagnosis (never at DEBUG in a way that could also capture `api_key` or full request kwargs — see Section 4b.5 and `02-RESEARCH.md`'s Security Domain table). If automatic retries are added in a later phase, cap at 1-2 attempts with the parse failure appended back into context so the model can self-correct, and always preserve the readable-error fallback on final failure.

### Async-First Design

`litellm.acompletion()` is the async entry point; `litellm.completion()` is synchronous and must never be called from inside a FastAPI route handler — it would block the single uvicorn event-loop thread and stall every other in-flight request, including the `/api/stream/telemetry` SSE stream this project depends on staying responsive.

**The one common mistake:** calling `asyncio.run(generate_reply(...))` from inside a route handler. FastAPI route handlers already run inside uvicorn's active event loop, so `asyncio.run()` there raises `RuntimeError: asyncio.run() cannot be called from a running event loop`. Always `await generate_reply(...)` directly inside the `async def` router/service function.

**Stream vs. await:** this system awaits, it does not stream. PLAN.md §9 deliberately chose one complete structured JSON response per turn ("Cerebras inference is fast enough that a loading indicator is sufficient") precisely because a structured JSON object cannot be validated against a Pydantic schema until the final token arrives anyway — streaming only benefits free-text output, not a schema-constrained reply that must parse as a whole. Await is the correct choice here; reserve streaming for a hypothetical future free-text-only chat mode with no structured-action extraction.

### Prompt Engineering Discipline

**System vs. user separation:** two system messages, not one — a static `SYSTEM_PROMPT` (the "SkyFleet flight director" role and behavioral instructions from PLAN.md §9) and a separate per-turn system message carrying `build_fleet_context()`'s live snapshot (budget, roster, telemetry). Keeping them separate means the static prompt text never needs to be regenerated or diffed just because live fleet numbers changed. History messages replay as alternating `user`/`assistant` roles loaded from `chat_messages`; the operator's new message is always the final `user` message.

**Few-shot:** inline, not dynamically retrieved. This phase has no retrieval system — no documents, no vector store (`02-RESEARCH.md`: "no RAG, no documents, no vector store — fleet context is a live struct read from `TelemetryCache` + SQLite, not retrieved"). If the schema's action shape needs stabilizing with an example, embed 1-2 short example turns directly as static text in `SYSTEM_PROMPT`; do not build a vector-backed example retriever for a single-call chatbot at this scale.

**Token budget:** `max_tokens=800` is set explicitly on every call (Section 4, Model Configuration) — never left unbounded in production. `gpt-oss-120b`'s ceiling is 131,072 output tokens; an unbounded call on a degenerate completion could run to that ceiling, multiplying per-call cost roughly 160x and stalling the operator's chat turn for a proportionally long time.

### Context Window Management

This is a Conversational (+ Structured extraction) system, so the applicable pattern is history truncation, not summarization or RAG chunking/reranking. `repository.get_recent_messages(db, limit=20)` caps replayed history to the last 20 turns. At this project's demo scale (single operator, no auth, course-capstone traffic), 20 turns comfortably fits inside `gpt-oss-120b`'s 131K-token window alongside the fleet-context snapshot, so no summarization/compaction pass is warranted in Phase 2. The "context" here is not documents to chunk but a live fleet-state struct rebuilt fresh every turn — already small and bounded by the fleet's own size (10 drones by default), so there is nothing to rerank or truncate beyond the message-count cap. If a future phase raises the history limit or fleet size enough to threaten the window, the next lever is trimming oldest turns further (already `limit`'s effect) before reaching for LLM-based summarization, which would add its own cost/latency/failure surface for a marginal token saving at this project's scale.

### Cost and Latency Budget

**Per-call cost estimate:** `openai/gpt-oss-120b` routed through OpenRouter to Cerebras is priced (per OpenRouter's model page, checked this session — verify current figures before relying on them, pricing changes independently of this document) at **$0.03/M input tokens** and **$0.17/M output tokens**, with a 131,072-token context window. At this phase's typical shape (~1-2K input tokens for fleet context + 20-turn history, ~200-400 output tokens per reply), a single chat turn costs roughly **$0.00005-0.0001** (input) + **$0.00003-0.00007** (output) — a small fraction of a cent per turn. At demo/course-capstone volumes (dozens of turns per session, not production-scale traffic), no per-call cost alarm is warranted for this phase. For comparison, direct Cerebras pricing (bypassing OpenRouter) is roughly 10x higher ($0.35/$0.75 per M) — the OpenRouter-routed path this project already uses is also the cost-optimal one.

**Caching:** none in Phase 2, deliberately. Exact-match caching would rarely hit — the fleet-context system message changes on effectively every call (battery levels, active missions update via the ~500ms telemetry simulator), so the same full prompt is essentially never repeated. Semantic caching is not justified at this call volume or stakes level (zero-stakes simulated fleet, per PLAN.md §9's auto-execution rationale). If a future phase introduces sustained higher-volume traffic, revisit — but Cerebras's inherent low per-token cost and fast inference are the first-order cost control here, not caching.

**Sub-task model routing:** Phase 2 has exactly one LLM call shape — there is no separate classification, routing, or summarization sub-task in scope to route to a cheaper model. `gpt-oss-120b` via Cerebras is already the cost-optimized choice for this single call type (fast inference, low OpenRouter-routed price vs. direct-provider pricing, shown above). No model-tiering is applicable until a later phase introduces a second, cheaper-shaped sub-task (e.g., a lightweight pre-classifier ahead of the main structured call).

## 5. Evaluation Strategy

> **Right-sizing note.** This is a zero-stakes, single-operator, simulated course capstone (Section 1b: virtual fleet, virtual budget, no auth, no real deliveries). The eval strategy is deliberately scoped to *deterministic, code-based checks running inside the existing pytest suite under `LLM_MOCK=true`*, plus a handful of gated live checks and one human UAT pass. No paid annotators, no hosted eval platform, no LLM-judge pipeline, no always-on production eval service. What is *not* right-sized down is the **validated-boundary rigor** — Section 1b flags architectural stakes as High because auto-execution has no confirmation gate, so D1/D2/D3 are non-negotiable gates even though a mistake costs nothing but a wrong number on a demo screen.
>
> **The key structural insight:** because the LLM only *proposes* and the backend executes through the real service layer, almost every dimension that would normally need an LLM judge is instead measurable as a deterministic assertion over `(canned LLM completion) → (executed actions, errors, resulting DB state)`. The reference dataset is therefore a set of raw completion strings replayed through the `stub_completion` fixture — free, offline, reproducible, CI-safe.

**Timeline:** fixtures are authored **in the same wave as `backend/app/chat/` itself**, not retrofitted after. Scenarios 6-11 in particular are the acceptance criteria for CHAT-07 and are already listed as Wave 0 gaps in `02-RESEARCH.md`'s Validation Architecture — building them alongside the code is what makes the validated-boundary pattern verifiable rather than merely asserted. Expand the set only from real observed failures during live runs; do not pre-build hypothetical coverage.

## 6. Guardrails

> **Guardrail vs. flywheel call.** Section 1b sets business stakes at Low but **architectural stakes at High**, because auto-execution has no confirmation gate — every AI proposal reaches the database with no human checkpoint. So the guardrails below are the checkpoint. Critically, **all five online guardrails are in-process and add no measurable latency**: none makes a second LLM call, none does I/O beyond the SQLite write the action already required. G1-G3 are code paths this phase is building anyway (Pattern 1); listing them as guardrails is naming the safety property they carry, not adding work.

### Online (Real-Time)

| # | Guardrail | Trigger | Intervention | Latency Cost |
|---|-----------|---------|--------------|--------------|
| **G1** | **Schema-validation gate** — `parse_reply()` runs `json.loads()` + `FlightDirectorReply.model_validate()` before any action is read | Non-JSON content, non-object payload, missing `message`, wrong types, invalid `action` enum | **Block, all-or-nothing.** Raise `LLMError` → router returns `HTTPException(502, {"reason": "llm_unavailable"})`. **Zero** actions execute — never best-effort partial execution from a partially-valid reply. Log the raw failed `content` at INFO for diagnosis. | ~0 (in-process parse) |
| **G2** | **Service-layer execution boundary** — every proposed action dispatched through `missions.service.launch_mission()` / `recall_mission()` / `roster.service.add_drone()` / `remove_drone()`; `app/chat/` never imports `*.repository` and never writes SQL | Any action, always — this is the sole write path | **Block the offending action, flag the rest.** The domain exception (`UnknownDroneError`, `InsufficientBudgetError`, `DroneAlreadyEnRouteError`, `NoActiveMissionError`, `DroneAlreadyTrackedError`) is caught per-action and rendered into `errors[]`; sibling actions in the same reply are unaffected. This is also what bounds prompt-injection blast radius (D8). | ~0 (same call a manual click makes) |
| **G3** | **Launch-argument completeness precondition** — before calling `launch_mission()`, require non-empty `zone` and finite `distance_km > 0` | A `launch` action with `zone=None`, `distance_km=None`, `<= 0`, `NaN`, or `inf` | **Block that single action** with `"Could not launch {drone_id}: missing zone or distance."` in `errors[]`. **Not a substitute for G2** — it only supplies the arguments `launch_mission()`'s signature requires; it must never grow into a second, weaker semantic-validation layer (`02-RESEARCH.md` Pitfall 3 / Section 3 Pitfall 3). | ~0 |
| **G4** | **Token/cost bound** — `max_tokens=800`, `temperature=0.2`, `stream=False` fixed on every `acompletion()` call | Every real (non-mock) call | **Cap.** Bounds a degenerate/repetitive completion that could otherwise run toward the 131 072-token ceiling — ~160x cost on one malformed generation and a proportionally stalled chat turn (Section 3 Pitfall 5). | ~0 (a request parameter) |
| **G5** | **Secret redaction** — `OPENROUTER_API_KEY` is read from env per call and never logged, never echoed into a response, never persisted to `chat_messages` | Every call; enforced by the "no `logger.debug()` of `api_key`, request headers, or full `acompletion()` kwargs" rule (Section 4b.5, `02-RESEARCH.md` Security Domain) | **Prevent by construction**, verified by assertion — the key value must be absent from `caplog.text` and every response body across the `tests/chat` suite (D8). | ~0 |

**Explicitly not an online guardrail:** a confirmation dialog before AI-executed actions. This is a decided product exclusion (`REQUIREMENTS.md` Out of Scope) — G1-G3 plus the D5 transparency requirement are the mitigation, with FE-09's inline confirmation cards (Phase 3) as the operator-facing surface. Also excluded: an LLM-based output-safety classifier — it would double per-turn latency and cost to screen content whose worst case (G2) is already bounded to "a mission a human could launch by clicking."

### Offline (Flywheel)

All flywheel metrics are computed from data the phase already persists — `chat_messages.content` + `chat_messages.actions` (JSON) + the per-turn structured log line (Section 7) — by a small ad-hoc script. No streaming pipeline, no warehouse, no scheduled job.

| Metric | Definition | Sampling Strategy | Action on Degradation |
|--------|-----------|-------------------|----------------------|
| **Action grounding failure rate** (D1) | Share of action-bearing turns with ≥ 1 rejected action, broken down by `exc.reason` | Review **100%** of turns from each live demo/UAT session — volume is dozens per session, so "sampling" is unnecessary | If `unknown_drone` dominates: the fleet-context snapshot isn't making the valid roster explicit enough — enumerate live `drone_id`s in `build_fleet_context()`. If `insufficient_budget` dominates: surface remaining kWh **and** the per-km cost constant in the context so the model can pre-compute. Both are prompt-context fixes, not model changes. |
| **Schema-failure rate** (D3) | `LLMError` (502) count per 100 live turns — **the CHAT-08 regression canary** | Every live turn; alongside every `litellm` version bump | **Any** non-zero rate in live use is a real signal, not noise. First check: is `response_format` still nested inside `extra_body` and reaching OpenRouter? A LiteLLM upgrade changing `extra_body` passthrough, or a silent revert to a top-level kwarg, is the most likely cause (`02-RESEARCH.md` Pitfall 5). Re-run the L1-L3 live prompts before assuming a model-quality issue. |
| **Transparency compliance rate** (D5) | % of executed actions whose `drone_id` appears in the turn's `message` | 100% of action-bearing turns, computed offline from `chat_messages` | Below ~95%: strengthen `SYSTEM_PROMPT` with an explicit instruction to name each drone and outcome, and add 1-2 inline few-shot example turns (Section 4b — inline, not retrieved). Re-measure over the next session. |
| **Multi-action turn coherence** (D6) | Count of turns proposing ≥ 2 actions; among them, count with contradictory pairs (launch + recall of the same drone) or with an end state inconsistent with the returned arrays | 100% of multi-action turns (rare by nature — worth reading individually) | Recurrent contradictions: add an explicit "do not propose conflicting actions for the same drone in one reply" line to `SYSTEM_PROMPT`. Any *inconsistent end state* is a code bug in `execute_actions()`'s sequencing, not a prompt issue — fix the loop, add a fixture. |
| **Per-turn cost & latency** (D9) | `response.usage` prompt/completion tokens and wall-clock ms per turn | Every live turn (logged, reviewed in aggregate at phase verification) | Compare against Section 4b's sub-cent/turn estimate. Sustained drift upward usually means history replay is growing — the first lever is lowering `get_recent_messages(limit=20)`, not summarization (Section 4b). |
| **Signal-metric divergence** | Turns where the operator immediately rephrases, repeats, or manually undoes what the AI just did | Read alongside the transcript during UAT | The early-warning system for eval gaps — a turn that passes every automated check but that the operator visibly rejected is exactly the case to promote into the reference dataset as fixture #15+. |

## 7. Production Monitoring

> **What "production" means here.** There is no fleet of servers and no on-call rotation — "production" is a dispatcher running one Docker container on localhost for a demo session (`REQUIREMENTS.md` Out of Scope explicitly excludes push/email/SMS alerting). So monitoring is **structured logging the operator and reviewer can read**, plus an opt-in local trace UI. Anything requiring a hosted platform, a second API key, or a paging integration is out of scope by design, not by omission.

**Tracing Tool:** **Structured per-turn logging via the existing `logging` module** (already configured in `app/main.py`, INFO level) is the required baseline and the only thing this phase depends on. **Arize Phoenix (self-hosted, localhost, opt-in) is the optional developer-facing trace UI** — install and setup in Section 5 → Eval Tooling, gated behind `PHOENIX_ENABLED=true`, instrumented via `LiteLLMInstrumentor` (LiteLLM is the client; the LangChain/LlamaIndex instrumentors do not apply). Phoenix must never be added to the runtime dependency set or the Dockerfile.

One INFO line per chat turn, emitted from `chat/router.py` after execution — deliberately capturing the fields every Section 6 flywheel metric is computed from, and deliberately **not** capturing `api_key`, request headers, or full `acompletion()` kwargs (G5):

```python
logger.info(
    "chat turn: latency_ms=%d prompt_tokens=%s completion_tokens=%s "
    "actions_executed=%d actions_failed=%d error_reasons=%s llm_mock=%s",
    latency_ms, prompt_tokens, completion_tokens,
    len(executed_missions) + len(executed_roster),
    len(mission_errors) + len(roster_errors),
    [e.split(":")[-1].strip() for e in mission_errors + roster_errors],
    mock_mode_enabled(),
)
```

**Key Metrics to Track:**

1. **Schema-failure rate** — `LLMError`/502 count per 100 turns. *The* CHAT-08 regression canary; the single most important number in this phase.
2. **Action rejection rate, by reason** — rejections per action-bearing turn, bucketed by `exc.reason` (`unknown_drone`, `insufficient_budget`, `drone_already_en_route`, `no_active_mission`). Distinguishes model grounding problems from a genuinely constrained fleet.
3. **Transparency compliance** — % of executed actions named in the turn's `message` (D5's entity-mention check, computed offline over `chat_messages`).
4. **Per-turn latency (p50/p95)** — wall clock around `generate_reply()`. Also the health check on the "Cerebras is fast enough that a loading indicator suffices" assumption behind the no-streaming decision (PLAN.md §9).
5. **Per-turn token usage** — prompt + completion tokens from `response.usage`; the leading indicator of history-replay growth and the input to the cost estimate.

**Alert Thresholds** — these are **investigate triggers surfaced in the console/logs**, not pages. There is no alerting infrastructure in this milestone and none should be added.

| Signal | Threshold | Response |
|--------|-----------|----------|
| Schema-failure (502 `llm_unavailable`) | **> 0** in any live session | Stop and check `extra_body` nesting of `response_format` + the `provider: {"only": ["Cerebras"]}` casing before anything else. Re-run the L1-L3 live prompts. This is the flagged CHAT-08 risk resurfacing. |
| Action rejection rate | **> 30%** of action-bearing turns | Read the reason breakdown. Grounding errors (`unknown_drone`) → enrich `build_fleet_context()`. Budget errors → likely a genuinely exhausted fleet budget, i.e. correct behavior; confirm before "fixing." |
| Transparency compliance | **< 95%** of executed actions named | Strengthen `SYSTEM_PROMPT` + add inline few-shot turns. Blocks FE-09's confirmation cards from being meaningful in Phase 3. |
| p95 turn latency | **> 5 s** | Check OpenRouter provider routing actually landed on Cerebras (a fallback provider is the usual cause), then history size. |
| Completion tokens | **> 1 500** on any turn (of the 800 cap → indicates the cap is missing) | Confirm `max_tokens=800` is present in the call kwargs — G4 regression. |
| Unhandled 500 from `POST /api/chat` | **any** | A hard bug: G1/G2 should convert every anticipated failure into a 502 or a readable `errors[]` entry. Capture the traceback, add a fixture, fix. |

**Smart Sampling Strategy:** capture is **100%** — turn volume is dozens per session, so nothing is dropped and there is no sampling *for capture*. Sampling is a **review prioritization filter** over the captured turns. Read these first:

1. Turns with a non-empty `errors[]` — every rejected action, since D1/D4 are where grounding and legibility fail together.
2. Turns that returned **502** — direct CHAT-08 evidence; keep the raw failed completion string.
3. **Multi-action turns** (≥ 2 actions) — rare and the highest-complexity path (D6).
4. Turns failing the offline entity-mention check (executed a drone the `message` never names) — the D5 transparency proxy firing.
5. Turns with latency > 5 s or completion tokens > 1 000 — degenerate-generation and provider-routing signals.
6. **Turns the operator immediately rephrased, repeated, or manually undid** — the signal-metric divergence filter. A turn that passes every automated check but that the human visibly rejected is the highest-value thing in the log: promote it into the reference dataset as the next fixture.

Anything surfaced by filters 1-6 that isn't already represented in the 14-scenario reference dataset becomes fixture #15+. That loop — real failure in, fixture out — is the whole flywheel, and it is the only expansion mechanism for the dataset (never hypothetical pre-coverage).
