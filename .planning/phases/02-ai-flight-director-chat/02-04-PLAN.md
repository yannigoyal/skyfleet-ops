<objective>
Turn the phase's failure requirements into an executable reference dataset: fourteen canned
completions replayed through the real endpoint, each asserting what executed, what was refused, what
the operator was told, and what the database looks like afterwards — plus the one structured log line
every offline flywheel metric is later computed from.

Purpose: CHAT-07 says a failing AI-proposed action must surface as a readable error the operator can
act on rather than crashing the turn or vanishing. That is a property of the whole request path, not
of one function, so it is provable only by replaying real completion strings end to end. Because the
LLM only proposes and the backend executes through the real service layer, almost every quality
dimension this phase cares about collapses into a deterministic assertion over canned input and
resulting database state — no judge model, no hosted platform, no API key, no network.

Output: the fourteen fixture files, the parametrised replay harness that is this phase's CI gate, the
transparency and secret-hygiene assertions, and the per-turn structured log line.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator message → LLM prompt → proposed actions | A hostile or injected instruction attempts to widen what the system will do |
| Chat turn → application log | Request-derived values reach a durable, human-readable sink |
| Chat turn → HTTP response body | Internal error detail reaches the client |

Out of scope project-wide: ASVS V2 Authentication, V3 Session Management, V4 Access Control, V6
Cryptography (single-operator demo, no auth boundary).

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-18 | Information Disclosure | `OPENROUTER_API_KEY` reaching a log record or a response body | high | mitigate | `TestSecretHygiene` sets a sentinel key value and asserts it appears in neither the captured log text nor the serialised response body; the per-turn log line carries only counts, timings, and reason keys, never credentials, headers, or provider call arguments |
| T-02-19 | Information Disclosure | Internal exception detail leaking through the errors array | medium | mitigate | Error strings are built from the domain exception's `reason` key plus the drone id, never from the exception representation; the harness asserts no error string contains a traceback marker |
| T-02-20 | Elevation of Privilege | Prompt injection widening the action surface | medium | mitigate | Fixture 14 asserts containment: the injected removal still traversed the roster service, so the active mission was recalled first and the outcome is a mutation the operator could already perform manually. Full prompt-injection hardening remains out of scope per PLAN.md's zero-stakes design |
| T-02-21 | Repudiation | A state change with no record of what was asked or what executed | medium | mitigate | Every turn persists both messages plus the executed-action JSON to `chat_messages` and emits one structured log line with the executed and failed counts and the reason keys — the audit trail that substitutes for the deliberately omitted confirmation dialog |
| T-02-22 | Tampering | Contradictory actions in one reply leaving ambiguous state | low | mitigate | Fixture 13 pins a single deterministic final mission status and active-mission count, so a change in execution order fails the test rather than passing silently |
| T-02-23 | Denial of Service | Log volume from high chat throughput | low | accept | One INFO line per turn at demo volumes of dozens of turns per session; no rotation or sampling warranted |
| T-02-SC | Tampering | npm/pip/cargo installs | n/a | accept | This plan installs zero new packages — the eval gate runs on the existing pytest suite with no new dependency, and AI-SPEC's optional Arize Phoenix tracing is deliberately not adopted |
</threat_model>
