`/api/chat`, the backend assembles live fleet context, gets a deterministic structured reply, executes
the proposed launch through the exact `missions.service` function manual dispatch uses, persists both
conversation turns, and returns one complete JSON response — served by the real FastAPI app.

existing `missions.service`, and the `app.main` mount. Proving that path first means the validated-
boundary architecture is committed and green before recall, roster delegation, the real provider call,
or the eval battery are layered on top of it.

Output: a complete `backend/app/chat/` package, the `litellm` dependency declaration, the `main.py`
wiring change, and the `backend/tests/chat/` test package with end-to-end coverage of the mock-mode
launch turn and the chat-history persistence path.

Build the thinnest complete path from `POST /api/chat` through the LLM seam, down to SQLite and the
existing missions service, and back out as one JSON response. One entry point, one action verb, no
recall path, no roster path.

Several files are near-verbatim ports of the sibling-branch reference; retrieve each with
`git show 2ba52a8:<path>` rather than retyping, then apply the corrections named below.

1. `backend/pyproject.toml` — add `"litellm>=1.96.0"` to `[project].dependencies` by running
   `uv add "litellm>=1.96.0"` from `backend/`, then `uv sync --extra dev`. This reconciles the
   lockfile with the `litellm-1.96.0` distribution already present in `.venv` but undeclared.

2. `backend/app/chat/models.py` — port from `2ba52a8` and add `LLMError`. Define
   `CHAT_ROLES = ("user", "assistant")` matching the `chat_messages.role` CHECK constraint, a
   `@dataclass(frozen=True, slots=True) ChatMessage` with fields `id`, `operator_id`, `role`,
   `content`, `actions: dict | None`, `created_at` plus a `to_dict()`, and
   `class LLMError(Exception)` with a class attribute `reason: str = "llm_unavailable"` — the same
   `reason`-attribute exception convention `missions/models.py` and `roster/models.py` use, so the
   router can build its 502 detail from `exc.reason` without a lookup table. The reference keeps
   `LLMError` in `llm.py`; move it to `models.py` so exceptions live where this codebase puts them.

3. `backend/app/chat/repository.py` — port from `2ba52a8`. Keep `DEFAULT_OPERATOR_ID = "default"`,
   the `_now()` UTC ISO helper copied verbatim from `roster/repository.py`, and a
   `_row_to_message(row)` that `json.loads` the `actions` column when it is not NULL.
   `append_message(db, role, content, actions=None, operator_id=DEFAULT_OPERATOR_ID)` inserts one
   row with a `uuid.uuid4()` id, storing `json.dumps(actions)` when `actions` is not None and NULL
   otherwise. `get_recent_messages(db, limit=20, operator_id=DEFAULT_OPERATOR_ID)` selects
   `ORDER BY created_at DESC, rowid DESC LIMIT ?` and returns `reversed(rows)` mapped to
   `ChatMessage` — most-recent-N, replayed oldest-first. Every statement uses `?` placeholders; never
   build SQL with f-strings or `%`-formatting. No `sqlite3.IntegrityError` translation is needed —
   `chat_messages` has no UNIQUE constraint.

4. `backend/app/chat/context.py` — port from `2ba52a8` with one addition. `build_fleet_context(db,
   cache) -> dict` reads `missions_repository.get_energy_budget`, `get_remaining_kwh`,
   `list_active_missions` and `roster_repository.list_roster`, then merges each roster drone with
   `cache.get(drone_id)` telemetry (`battery_pct`, `altitude_m`, `speed_kmh`, `status`) exactly as
   `roster/router.py::_entry_response` does, and returns a dict with keys `energy_budget_kwh`,
   `remaining_kwh`, `active_mission_count`, `active_missions`, `roster`, `average_battery_pct`.
   Addition: also include `energy_cost_per_km_kwh` sourced from
   `app.missions.models.ENERGY_COST_PER_KM_KWH`, so the model can pre-compute whether a proposed
   distance fits the remaining budget instead of guessing (AI-SPEC §6 names this as the fix for
   budget-rejection dominance; wiring it up front is free). This module is read-only and performs no
   writes, which is why it reads through the missions and roster persistence modules directly —
   the same convention `missions/router.py::get_fleet_status` and `roster/router.py`'s GET handler
   already follow. The service-layer-only rule applies to the write path in `router.py`, not here.

5. `backend/app/chat/llm.py` — port from `2ba52a8` with three corrections. Keep
   `MODEL = "openrouter/openai/gpt-oss-120b"`, the full `RESPONSE_SCHEMA` verbatim (the `strict: True`
   json-schema object with `message` / `missions` / `roster_changes`, every property also listed in
   `required`, `additionalProperties: False`, and `zone` / `distance_km` typed as nullable unions),
   `SYSTEM_PROMPT`, the `MissionAction` / `RosterChange` / `FlightDirectorReply` Pydantic models using
   `Literal` for the `action` fields, `mock_mode_enabled()` reading
   `os.environ.get("LLM_MOCK", "").strip().lower() == "true"`, `parse_reply()`, `build_messages()`,
   and `mock_reply()`. Corrections:
   - `PROVIDER_ROUTING = {"only": ["Cerebras"]}` with a capital C, matching Cerebras's own published
     OpenRouter integration example. The reference uses lowercase; OpenRouter's matcher casing is
     undocumented, so match the authoritative form.
   - Import `LLMError` from `.models` instead of defining it here.
   - Add two module constants `TEMPERATURE = 0.2` and `MAX_TOKENS = 800` for plan 02's call to use.
   Also extend `SYSTEM_PROMPT` with one instruction: the reply's `message` must name every drone id
   and every action it takes, so a dispatcher reading only the transcript knows what executed. This
   is the payload the Phase 3 confirmation cards render from and the AI-SPEC D5 transparency gate
   asserts on.
   `generate_reply(fleet_context, history, user_message)` keeps the mock early-return
   (`if mock_mode_enabled(): return mock_reply(fleet_context, user_message)`) and, for the real
   branch, raises `LLMError("live LLM calls are not wired yet - set LLM_MOCK=true")` for now. Plan 02
   replaces that single raise with the real provider call; the seam and its signature do not change.

6. `backend/app/chat/router.py` — start from `git show 2ba52a8:backend/app/chat/router.py` and cut it
   down to the launch path. Define `ChatRequest(BaseModel)` with a single field `message` typed as
   `Annotated[str, StringConstraints(strip_whitespace=True, min_length=1)]` so an empty or
   whitespace-only body is rejected with 422 at the Pydantic boundary before any LLM call — mirroring
   `AddDroneRequest.drone_id`'s `Field(min_length=1)` guard in `roster/router.py`. Import
   `from app.missions import service as missions_service` and `from app.missions.models import
   MissionError`. Define a module-level (not closure-nested) private helper
   `async def _execute_mission(db, cache, action) -> tuple[dict | None, str | None]` that, for
   `action.action == "launch"`, first requires a non-empty `action.zone` and a finite
   `action.distance_km` greater than zero — returning
   `(None, f"Could not launch {action.drone_id}: missing zone or distance.")` when that precondition
   fails — then calls
   `await missions_service.launch_mission(db, cache, drone_id=action.drone_id, zone=action.zone,
   distance_km=action.distance_km)` inside a `try/except MissionError`, returning
   `(None, f"Could not launch {action.drone_id} to {action.zone}: {exc.reason}.")` on failure and
   `({"drone_id": ..., "action": "launch", "zone": ..., "distance_km": ...}, None)` on success. Any
   other `action.action` value returns
   `(None, f"Could not {action.action} {action.drone_id}: not wired in this slice.")` — plan 03
   replaces that arm with the real recall branch. Never call `missions_service.auto_assign_mission`
   or `find_eligible_drone`: chat always carries an explicit `drone_id`, so it never touches the one
   function with a known eligibility race.
   `create_chat_router(db: Database, cache: TelemetryCache, source: TelemetrySource | None = None)
   -> APIRouter` builds `APIRouter(prefix="/api", tags=["chat"])` with one `@router.post("/chat")`
   handler that: awaits `build_fleet_context(db, cache)`; awaits
   `repository.get_recent_messages(db, limit=20)`; awaits `llm.generate_reply(...)` inside a
   `try/except LLMError` that raises
   `HTTPException(status_code=502, detail={"reason": exc.reason, "detail": str(exc)})`; loops
   `reply.missions` one action at a time (sequential `await`, never a pre-validated batch, so a later
   launch correctly fails once an earlier one consumed the budget) collecting successes into
   `executed_missions` and failure strings into `mission_errors`; iterates `reply.roster_changes` into
   an empty `executed_roster` list for now (plan 03 fills it); then appends the user turn via
   `repository.append_message(db, "user", request.message, actions=None)` and the assistant turn via
   `repository.append_message(db, "assistant", reply.message, actions={"missions":
   executed_missions, "roster_changes": executed_roster})`; and returns
