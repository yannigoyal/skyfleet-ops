<objective>
Deliver the removal slice: an operator can remove a drone from the fleet roster with a single
`DELETE /api/roster/{drone_id}`, and if that drone is mid-delivery the mission is automatically
recalled first so the system is never left with an orphaned in-flight mission.

Purpose: this is the second vertical slice, expanding out from the proven tracer path. It adds the
first cross-module service dependency in the codebase (`roster.service` → `missions.service`) and
the accepted two-transaction ordering that goes with it.

Output: `roster.service.remove_drone()`, the `DELETE /api/roster/{drone_id}` route, and service-
and router-level coverage of the auto-recall, idempotency, and telemetry-failure paths.
</objective>

  <action>
Add the removal path to the service layer and expose it through the router.

In `backend/app/roster/service.py`, add narrow function imports at module top —
`from app.missions.repository import get_active_mission_for_drone` and
`from app.missions.service import recall_mission`. Use these two named imports rather than importing
the `app.missions` package, so the new cross-module coupling surface stays greppable and minimal
(RESEARCH Open Question 2). The direction is one-way — the missions package must never import back
from the roster package.

Then add `async def remove_drone(db: Database, source: TelemetrySource | None, drone_id: str) -> None`
implementing D-03 in this exact order:
1. Check first — `if await get_active_mission_for_drone(db, drone_id) is not None:` then
   `await recall_mission(db, drone_id)`. Querying before acting keeps the flow readable and avoids
   using `NoActiveMissionError` as control flow (RESEARCH Open Question 1). Do not catch
   `NoActiveMissionError` here; the guard makes it unreachable on this path.
2. `await repository.remove_drone(db, drone_id)` — this raises `UnknownDroneError` if no row was
   deleted; let it propagate for the router to translate.
3. Telemetry sync, mirroring the add path: `try: await source.remove_drone(drone_id)` guarded by
   `if source is not None`, `except Exception: logger.exception("telemetry sync failed for remove_drone(%s)", drone_id)`. It must sit after the deletion has committed and outside any `db.transaction()` callback (D-04).

Keep recall and deletion as two sequential awaits. Do not attempt to span both tables in one
transaction: `Database` exposes no nested-transaction or shared-connection primitive, and building
one would require changing both repositories' signatures to accept a raw `sqlite3.Connection` — a
refactor outside this phase. The instance-wide `asyncio.Lock` already prevents a third writer from
interleaving; the residual crash window between the two awaits is the accepted tradeoff recorded in
D-03's costly reversibility rating. Recall-before-delete is deliberately chosen so the failure mode
is "mission recalled, drone still listed" (safe, and a DELETE retry finishes the job) rather than
"drone gone, mission still flying".

In `backend/app/roster/router.py`, add the handler
`@router.delete("/{drone_id}", status_code=204)` whose body calls
`await service.remove_drone(db, source, drone_id)` inside `try/except RosterError as exc: raise _error_response(exc) from exc`, returning `Response(status_code=204)`. The existing `_ERROR_STATUS`
table already maps `unknown_drone` to 404 and needs no new entry — the check-first guard means the
recall step cannot surface a mission-layer failure to the operator.

In `backend/tests/roster/test_service.py`, add `class TestRemoveDrone` (no-active-mission path,
unknown drone raises, `FakeSource` deregistration) and `class TestRemoveDroneWithActiveMission`.
For the latter, use `app.missions.repository.create_mission` against the `db` fixture to put a real
`en_route` mission on `FALCON-01`, call `roster.service.remove_drone`, then assert via
`missions.repository.get_active_mission_for_drone` that it returns `None`, query the `missions` row
directly for `status == "recalled"`, and query `mission_log` for a row with `action = 'recall'`.
Add a budget assertion: capture `missions.repository.get_remaining_kwh(db)` before and after and
assert the delta equals the mission's `energy_cost_kwh` being released, so a hidden budget movement
introduced by the removal path would fail the test.

Run `uv run --extra dev ruff check app/ tests/` from `backend/` and fix any findings.
