<objective>
Close the one blocking gap in Phase 1: `DELETE /api/roster/{drone_id}` currently returns an
unhandled HTTP 500 instead of 204 when a drone's in-flight mission is resolved by another writer
between `roster.service.remove_drone`'s active-mission check and its `recall_mission` call.

The check-then-act flow is correct and stays (D-03's auto-recall, check-first, no
exception-as-control-flow). What is missing is the one thing check-then-act always needs: handling
the case where the world changed inside the window. `app.missions.models.NoActiveMissionError` is a
`MissionError`, not a `RosterError`, so the roster router's `except RosterError` handler never sees
it. In production `run_delivery_scheduler` ticks every 5 seconds and can flip an overdue `en_route`
mission to `delivered` inside exactly that window — the security auditor live-reproduced this
against the real app (DELETE returned 500, a retry returned 204).

Purpose: ROADMAP Phase 1 Success Criterion 2 and ROST-02 promise a reliable 204/404 contract, and
Phase 2's AI flight director is planned to call `roster.service.remove_drone` directly for
AI-triggered removals — the same race would surface as an opaque chat failure if left unfixed.

Output: a narrowed guard around the recall step, a log record so the race stays diagnosable, and
regression tests at both the HTTP and service layers that interleave a real mission resolution into
the window and prove the removal now succeeds.
</objective>
