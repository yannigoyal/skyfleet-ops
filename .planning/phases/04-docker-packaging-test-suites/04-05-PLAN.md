<objective>
Close gap G-04-2: both start scripts launch the container detached and open the browser
immediately, so the browser's first request always lands during the 2-3s container boot window
and the operator sees a "page is not working" error before the app appears.

Purpose: the single-command launch is the project's headline promise (PLAN.md section 11). A
launch that reliably shows a broken page for the first few seconds undermines it, and the fix is
a wait the scripts simply never had — `docker run -d` returns when the container process is
created, not when uvicorn is accepting connections.
Output: a bounded, tested readiness poll wired into both scripts between container start and
browser open, so the browser is only opened once the server answers.
</objective>

    - Endpoint already answering when the poll starts: exits 0, promptly.
    - Endpoint starts answering roughly 2s after the poll starts: exits 0, and the measured

  <action>
    Write the test first, watch it fail against the missing helper, then write the helper.

    Create `scripts/wait_for_health.sh`. It takes the URL as `$1` (required — fail with a usage
    message if absent) and an optional timeout in seconds as `$2`, defaulting to 60. Compute a
    deadline from `date +%s` plus the timeout, then loop until the deadline: each iteration runs
    `curl` against the URL with `-fsS --max-time 2 -o /dev/null` and exits 0 on success,
    otherwise sleeps a quarter second and retries. On reaching the deadline, exit 1. Use
    `set -uo pipefail` — deliberately without `-e`, because a failing `curl` is the expected
    steady state of this loop, not an error. Before the loop, if `curl` is not on PATH, exit 2
    so the caller can distinguish "tool missing" from "server never answered" and skip the wait
    instead of burning the full timeout. Keep `-o /dev/null` and omit `-v`: the poll must not
    echo response bodies or headers into terminal scrollback, since this script runs immediately
    after a container started with `--env-file .env` (T-04-05-01).

    Create `scripts/tests/test_wait_for_health.sh` covering the three cases in `<behavior>`. It
    needs no Docker. Resolve the helper path relative to `BASH_SOURCE` so the test runs from any
    working directory. Allocate ports by binding port 0 with a one-line `python3 -c` socket call
    and reading back the assigned port, rather than hardcoding one, so the test does not collide
    with whatever else is running. Serve a temporary directory containing an `api/health` file
    via `python3 -m http.server <port> --bind 127.0.0.1 --directory <docroot>` — that makes
    `/api/health` answer 200 with no application involved. For the late-start case, background a
    subshell that sleeps 2 then starts the server, and clean it up afterwards with a
    `pkill -f` match on the port (killing the subshell alone leaves the server child alive).
    Accumulate failures into a counter, print a one-line reason per failed case, and exit
    non-zero if any case failed. Keep total runtime under about 10 seconds.

    Wire the helper into `scripts/start_mac.sh` immediately after the `docker run -d` block and
    before the existing "SkyFleet Ops is running at ..." message — that message should only print
    once it is true. Print a line saying the script is waiting for the health endpoint, then
    invoke the helper with the health URL built from the existing `PORT` variable and a 60s
    timeout, capturing its status with a trailing `|| status=$?` assignment so `set -e` does not
    abort the script on a non-zero exit. Branch on the three exit codes: 0 prints a short ready
    line; 2 notes that `curl` was not found so the wait was skipped and the page may need a
    refresh; anything else warns that the server has not answered yet, names
    `docker logs skyfleet-ops` as the place to look, and says the browser is being opened anyway.
    In all three cases the script continues to the existing leftover-volume notice and `open`
    call — a slow or unhealthy container must degrade to today's behavior, never to a script that
    exits non-zero or hangs (T-04-05-02).

    Do not change the container start itself, the bind mount, the leftover-volume notice, or the
    `--build` handling. This plan adds a wait; it does not restructure the launch.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| start script → local container HTTP | The scripts poll `http://localhost:8000/api/health` on a container started with `--env-file .env`; response content must not reach terminal scrollback or CI logs |
| operator terminal → readiness loop | An unbounded loop would hold the operator's shell hostage on a container that never becomes healthy |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-05-01 | Information Disclosure | `scripts/wait_for_health.sh` curl invocation | low | mitigate | Poll runs with `-o /dev/null` and without `-v`, so no response body or header from a container launched with `--env-file .env` is echoed into scrollback or logs |
| T-04-05-02 | Denial of Service | readiness loop in both start scripts | medium | mitigate | Loop is deadline-bounded (60s default) and both callers treat timeout as a warning that still proceeds, so an unhealthy container cannot hang the launch |
| T-04-05-03 | Tampering | URL argument to `wait_for_health.sh` | low | accept | The URL is built by the start scripts from their own `PORT`/`$Port` constant, never from external input; the helper is a local operator tool with no network-exposed surface |
| T-04-05-04 | Spoofing | localhost health poll target | low | accept | A local process could bind port 8000 before the container and satisfy the poll, opening the browser onto the wrong app. Accepted: an attacker able to bind the operator's loopback ports already has local code execution, which is outside this single-operator dev tool's threat model |
| T-04-05-SC | Tampering | package installs | low | accept | This plan installs no packages — no npm, pip, cargo, or `uv add` step. The behavioral test uses only the Python standard library's `http.server` plus `curl`. No package legitimacy checkpoint applies |
</threat_model>
