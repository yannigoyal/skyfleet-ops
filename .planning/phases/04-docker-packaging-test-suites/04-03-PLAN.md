<objective>
Turn the E2E directory from a scaffold with one health check into a suite that actually
exercises the console: a fresh fleet, roster mutation, and mission launch and recall — all
driven through the real container built from the production Dockerfile.

Purpose: TEST-04 names six scenarios and only a health-check placeholder exists. This plan
delivers the first three plus the execution discipline the remaining three depend on. That
discipline is load-bearing rather than incidental: seven specs share one app container holding
one mutable energy budget, roster, and mission list, so without serialization and per-spec
cleanup the suite would report failures that are really cross-test interference — and the usual
response to that is raising timeouts until it goes quiet, which produces a green suite with no
detection power at all.
Output: a serialized Playwright config, a shared helper module, three new specs, and a verified
claim that the browser runtime lives only in the test-only compose file and never in the
production image.
</objective>

    Establish the execution model the whole suite depends on, then prove it with the first
    scenario.

    In `tests/playwright.config.ts`, set `fullyParallel: false` and `workers: 1`. Seven specs
    share exactly one app container holding one energy budget, one roster, and one mission list,
    so parallel workers would interleave mutations and produce failures that look like product
    bugs but are test-harness artifacts. Leave `testDir`, `reporter`, `baseURL`, `trace`, and the
    chromium project untouched, and leave `retries` at its existing CI/non-CI values — raising
    retries is the standard way a flaky suite gets quietly converted into a suite with no
    detection power, and this plan's prohibition rules it out.

    Create `tests/specs/helpers.ts` as the shared module every spec imports. Playwright's default
    test-file matcher only picks up `*.spec.ts` / `*.test.ts`, so a plain `helpers.ts` inside
    `specs/` is treated as a module, not a suite. Export five functions:

    - `getFleet(request)` — GET `/api/fleet`, return the parsed body (`energy_budget_kwh`,
      `remaining_kwh`, `active_mission_count`, `missions`).
    - `getRoster(request)` — GET `/api/roster`, return the parsed body.
    - `readHeaderRemainingKwh(page)` — read the header's energy-budget text and parse the
      remaining figure out of the `{remaining} / {total} kWh` form with a numeric regex. Return a
      number so callers can compare before and after rather than matching a literal.
    - `pickIdleDrone(request)` — read the roster and the active mission list, and return the id
      of a roster drone that has no `en_route` mission. Throw a clear error if every drone is
      busy, so a caller fails with a diagnosable message instead of an undefined selector value.
    - `restoreFleetState(request, { addedDroneIds, launchedDroneIds })` — recall each launched
      drone via DELETE `/api/fleet/missions/{drone_id}` and remove each added drone via DELETE
      `/api/roster/{drone_id}`, tolerating a non-2xx on each individually (the mission may have
      already been recalled by the spec body, or delivered by the background scheduler). This is
      the function that makes the suite re-runnable: without it the second run starts from a
      roster and budget the first run left behind.

    Create `tests/specs/fresh-start.spec.ts` for TEST-04 scenario 1, using the `health.spec.ts`
    import line verbatim. Assert three things:

    - The default fleet is present: `GET /api/roster` includes `FALCON-01` through `FALCON-10`,
      and after `page.goto("/")` the roster panel shows a row for each. The roster panel renders
      exclusively from SSE snapshots, so ten visible rows is itself proof the telemetry stream
      delivered — this assertion does double duty for the "telemetry is streaming" clause.
    - The energy budget is 500 kWh: assert on `energy_budget_kwh` from `GET /api/fleet` and on
      the header containing the total `500.0 kWh`. Assert on the **total**, never the remaining
      figure — remaining is shared mutable state that earlier specs legitimately reduce, and an
      absolute assertion on it would make this spec depend on file ordering.
    - The stream is live, not merely rendered once: assert the connection indicator reads `Live`
      with an exact-text match, and additionally poll a single drone's battery percentage until
      it differs from the first value read. The simulator emits a new reading roughly every
      500ms, so a change inside a generous timeout is the difference between proving the stream
      is flowing and proving one snapshot arrived. Give it a wide timeout rather than a tight
      one; the point is liveness, not latency.

    This spec mutates nothing, so it needs no restoration — but write it so it holds regardless
    of what ran before it, which is what the total-versus-remaining distinction buys.

    Finally, verify TEST-05 by inspecting the artifacts rather than the intent. Confirm the test

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| E2E harness container → app container | Test traffic crosses the compose network into the same production image the start scripts run |
| Repository `.env` → test app container | The test compose supplies its own environment rather than the operator's real credentials |
| Suite green signal → phase completion claim | A passing run is treated as evidence the console works, without anyone re-deriving it |
| Shared app container state → per-spec assertions | One mutable budget, roster, and mission list is read and written by every spec in the run |
